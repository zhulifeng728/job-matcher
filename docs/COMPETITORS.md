## 三、我的结论

### 3.1 真正的差异化只有两个

1. **浏览器扩展** —— 上面四个项目全都没有。它们都要么是 CLI（复制粘贴命令行），要么是网页（手工上传简历 + 粘贴 JD）。扩展把「获取 JD」这一步降到一次点击。
2. **零依赖部署** —— 别人要 Docker / Playwright / LaTeX / Bun，我这边 `node src/server.js` 就起来了。对「想自己跑一个试试」的人来说门槛差一个数量级。

### 3.2 内容深度上确实落后

Career-Ops 的 6 个评估模块（职位总结 / 简历匹配 / 职级策略 / 薪酬调研 / 个性化建议 / 面试准备 STAR+R）比我的信息密度高。它靠的是 Claude Code 的推理能力，我用规则实现，天花板低。

**但有个反过来的优势**：它必须有 AI 才能用，我的核心功能不依赖 AI 也能跑（评分、故事骨架、职级判断、26,000 字复习文档），配了 AI 只是让内容更深。**别人的产品是「没 key 就不可用」，我的是「没 key 也能用，有 key 更好」。**

### 3.3 差距清单（按优先级）

| 缺口 | 影响 | 工作量 |
|---|---|---|
| 多简历版本管理 | 中（投不同方向要不同版本） | 中 |
| ATS PDF 导出 | 中（能直接投出去） | 中 |
| 投递结果反哺评分权重 | 高（**别人都没做**，独特点） | 大 |
| AI 重写简历（而非重排） | 高（本质差距） | 大（要先有可用模型） |

第 3 项其实是真正的机会：**用「哪些维度带来面试」的真实数据校准评分权重**。
现在的权重是我拍脑袋定的（架构 25 / AI 25 / 小程序 15 / 后端 15 / 系统设计 10 / 团队管理 10）。
跑一段时间后可以算：每个维度的得分与「进入面试」的相关性，用这个反推权重。
这件事 Career-Ops 和 Resume-Matcher 都没做 —— 它们的评分是静态的。

## 四、这一轮补了什么

### 4.1 面试故事库

Career-Ops 的核心卖点。从简历要点自动拆 STAR 骨架，按 5 类归类，跨岗位复用。

实测（16 条简历要点）：

| 类型 | 数量 |
|---|---|
| 技术攻坚 | 6 |
| 效率提升 | 2 |
| 团队协作 | 1 |
| AI 落地 | 1 |
| 线上问题 | 0 ← 会提示补 |

归类踩的坑：裸「管理」会匹配到「管理系统」，把技术条目误判成团队协作。顺序必须是 AI > 线上 > 效率 > 技术 > 团队。

### 4.2 职级策略与谈薪

| 判断 | 条件 |
|---|---|
| 降级 | 岗位要求年限 < 你 - 3，或岗位名带「实习/初级/助理」 |
| 上浮 | 岗位要求年限 > 你 + 2，或岗位名带「负责人/总监/架构师」而你年限不够 |
| 平级 | 其余 |

薪资解析覆盖 `45-65K·15薪` / `30k-50k` / `4.5-6.5万` / `35k~55k`，单位支持 K / 千 / 万 / 元，能识别月数并算年包。

修了两个 bug：
- `5 年要求 + 7 年经验` 被判成降级（阈值该是 3 年不是 2 年）
- `30k-50k` 解析成 `30-30K`（单位在数字后面时正则失配）

## 五、第二轮：补上「能投出去的简历」

### 5.1 上一轮漏掉的核心问题

产品分析得很细，但**产不出可直接投递的东西** —— 用户拿到分数和建议，还得自己回去改简历。
原项目 `resume-ai-optimize` 有 AI 重写 + 版本对比，这一版只是把要点重排了顺序。这才是「不尽人意」的根。

### 5.2 设计依据

参考 [JobShinobi 的 ATS 关键词研究](https://www.jobshinobi.com/blog/ats-optimized-resume-keyword-density-explained)，
三条能落地的原则：

| 原则 | 落地方式 |
|---|---|
| **覆盖率 > 密度** | 算 must-have 命中率，不追密度百分比 |
| **claim + proof** | 关键词在技能区声明、在经历区给证据 |
| **密度只做烟雾报警器** | 0 次=漏了，6-9 次=偏多，10+ 次=堆砌 |

文章里还有一个关键数据：招聘方筛简历平均 **7.4 秒**（Ladders 眼动研究），
所以简历必须**可扫读**，不是信息越多越好。

### 5.3 实现的四件事

**① 关键词提取与分级**（`src/generate.js`）
从 JD 提关键词，按四类（工具/方法/领域/职责）分，权重看三点：
出现在「任职要求」段 +14、重复出现 +2/次、出现在「职责」段 +6。
权重 ≥24 的进入 must-have（上限 15 个）。

**② 简历生成**
按 ATS 友好结构产出完整 Markdown：

```
# 姓名
求职意向：岗位 ｜ N 年经验 ｜ 城市 ｜ 学历
## 核心优势      ← 3-4 句，含 must-have 关键词
## 专业技能      ← 分组：技术栈 / 工程与流程 / 业务领域
## 工作经历      ← 按「公司 · 职位」+ 在职时间分组，组内按 JD 相关度排序
## 项目经历      ← 来自「项目经历」段，标题抽项目名
## 教育经历
```

一条铁律：**JD 要求但简历里没有证据的关键词，绝不写进正文**，只列进「需补齐」清单。

**③ 关键词位置矩阵**
每个 must-have 标注出现在哪个位置（摘要 / 技能 / 经历），一眼看出「声明了但没证据」的情况。

**④ 导出三条路**
- 复制 Markdown
- 下载 `.md`
- **打印视图 → 浏览器存 PDF**（A4 @page 样式，文本层完整，ATS 能解析）

> 为什么用 HTML 打印而不是自己拼 PDF：手写 PDF 二进制很容易做出图片型 PDF，
> ATS 读不到文字层。浏览器打印产出的 PDF 文本层是完整的。

### 5.4 版本管理

参考原项目的 `ResumeVersion` 设计：
- 每版记录「为哪个岗位生成」
- `isSelected` 标记采用，不删旧版可回退
- 未采用的自动留最近 6 个
- **内容完全相同不新增版本**（连续点几次生成不该刷出 5 个一样的）

### 5.5 修掉的问题

| 问题 | 原因 | 修法 |
|---|---|---|
| 技能区只有 6 个词 | 只取了「JD 提到 ∩ highlight.keywords」 | 再加简历全文匹配 + 技术词库补全 |
| 密度误报「Vue 6.5%」 | 中文无空格，按空格算词数分母荒谬 | 改绝对次数 + 章节分布 |
| 简历没有公司/时间 | 解析器丢弃了组织行 | 解析「2021.03 - 至今  公司  职位」并让要点归属条目 |
| 公司名判成职位 | `clean()` 把多空格压成单空格，按双空格拆分失效 | 改按单空格 + 职位词判定 |
| 要点在正文重复三次 | 项目区复用了经历区的要点 | 项目只用 `from==='project'` 且排除摘要已引用的 |
| 教育只有「本科」 | 只存了学历层次 | 存整行「时间 学校 专业 学历」 |

## 六、第三轮：用真实结果校准评分权重

### 6.1 为什么做这个

前两轮补的是「分析」和「产出」。但所有竞品的评分权重都是**静态**的 ——
Career-Ops 的 10 个维度权重、Resume-Matcher 的关键词权重、ai-job-search 的 ATS 打分，
都是产品方定的，用户投了 100 个岗位之后，权重一分不变。

这是唯一一个「用户用得越久、产品越准」的机制，也是最难被抄的
（需要真实投递数据，冷启动做不出来）。

### 6.2 做法

```
进面/offer 的岗位  → 组 A
投了没消息的岗位   → 组 B
逐维度比较 A 和 B 的平均得分
lift 越大 → 这个维度越能区分结果 → 权重上调
```

演示账号的实测结果（6 投 / 2 面 / 1 offer，置信度低）：

| 维度 | 当前 → 建议 | 进面组 / 没消息组 |
|---|---|---|
| 前端架构与工程化 | 25 → 28 | 100% / 79% |
| 后端与全栈能力 | 15 → **21** | 50% / 3% |
| AI 应用落地 | 25 → 26 | 50% / 34% |
| 系统设计与性能 | 10 → **4** | 0% / 44% |

「后端与全栈」在进面的岗位里平均 50%、没消息的只有 3% —— 这个维度最能区分结果，
所以权重上调。「系统设计与性能」正好相反，下调。

### 6.3 四道防线（小样本的诚实处理）

| 防线 | 阈值 | 理由 |
|---|---|---|
| 样本门槛 | 已投 ≥6 且进面 ≥2 | 低于这个数，任何「规律」都可能是巧合 |
| 调整上限 | 单维 ±60% | 防止一两个极端样本把权重带偏 |
| 置信度 | ≥20 投且 ≥5 面才算「中」 | 不假装精确 |
| 手动应用 | 必须点确认，可恢复 | 不替用户做决定 |

界面上明确写：**「这是启发式推断，不是因果结论」**。

### 6.4 已知局限

1. **幸存者偏差**：进面的岗位可能是因为岗位本身好投、HR 响应快，不一定是能力匹配
2. **样本混淆**：不同岗位的 JD 长度、公司规模都会影响，没有做控制变量
3. **反馈滞后**：从投递到面试通常 1-2 周，数据更新慢

这些局限不做技术包装 —— 在 UI 里如实说明，比假装科学更可信。
